Two problems, one cut. The store is read at every cold start and the
annotation history dominates it, so the read cost is paid by every session
that never needed the history. And the append-only rule cannot be checked:
every append modifies the same file, so an in-place amendment of a landed
entry is indistinguishable in shape from a legitimate append. That rule has
already been broken once and was caught by a human reading a diff.

The cut. A small bets file keeps version, convention, scored and open, and
stays mutable, because scoring a bet legitimately moves it between blocks.
Each annotation entry becomes its own file, named so that the file name is
derivable from the entry id, and is never touched again after the apply
that lands it. The old single-file path keeps a pointer, because several
references to it sit in dossier material that is historical and not
editable.

Why one file per entry rather than range shards. Per entry, append-only
stops being a discipline and becomes a property a check can enforce: no
file under the annotation directory may ever appear as modified or deleted.
Appends stop being able to conflict, since two lanes appending produce two
new files rather than two hunks in one. And the ratifying commit of a
single entry becomes an ordinary git fact about one file instead of a
needle in a very large diff. The cost is file count, which at the project's
current entry cadence grows fast; the answer is a named trigger rather than
an improvisation later, so bucket the directory once the entry count
crosses a few hundred.

The relocation check is the instrument this project already owns from the
Lean split: the concatenation of the annotation files, in id order, must
reproduce the annotation block of the pre-split revision byte for byte.
Written that way it does not expire at the split commit. It keeps proving,
on every run, that no historical entry has been edited since, which is the
same invariant the append-only check enforces for everything added later.

Sequencing constraint, not a preference. The work touches script and CI
paths that are not on the bookkeeping path list used by dispatch validity
predicates, so it must not land while a dispatch pinned before it is in
flight; a session started against the older pin would correctly stop and
report. Land it in a window where no dispatch is open.

Two questions this item surfaces and one it must not decide. Whether the
short reference form becomes canonical and the date-bearing long form is
kept only in the id field: dangling refs already exist in the store, and
they share one shape, correct number and wrong date component, which is
evidence that the date component carries no information and only breaks.
Whether the directory bucketing trigger is set by entry count or by time.
Not to be decided here: the standing tension between the registration
convention, which says edits append and never rewrite, and the fact that
scoring a bet moves an entry between blocks. That tension predates this
item, and a storage change is the wrong instrument for settling it.

The inventory of malformed refs belongs in a ledger entry, not in this
file. This item only requires that the validator would catch them.

## Final summary

Executed 2026-07-31 (ANN-20260731-87). ledger.yaml is now a pointer stub; the mutable bets file is ledger/bets.yaml and the annotation history is ledger/annotations/, one strictly append-only file per entry named <id>.yaml. The relocation is proved rather than asserted: the pinned entries concatenated in ascending sequence order reproduce the pre-split annotations body byte for byte, and the check reaches back to the pre-split pin on every run, so it does not expire at the split commit. scripts/ledger_check.py carries the relocation check, a validator (filename == id, unique ids, contiguous sequence, ref integrity by namespace) and an append-only check; all three run in CI as a ledger job. Four historical dangling refs are grandfathered on a named allowlist that is not a repair channel, and the inventory lives in ANN-20260731-87. Ids, citation vocabulary and the byte content of every existing entry are unchanged. Carried open by design: Q1 short-vs-long reference form and Q2 the bucketing trigger; the bet registration-versus-scoring tension is explicitly not settled here.
